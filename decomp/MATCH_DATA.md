# Data-matching prompt — ico (PS2)

Paste this as the first message of a fresh Claude Code session to start
a data-section matching pass (.sdata / .lit4 / .rodata / .data).

Where the function-matching prompt at `decomp/MATCH.md` claims one .text
subseg at a time, this prompt claims one TU's **data sidecar** at a time:
convert the auto-generated byte-array definitions in `src/<TU>_data.c`
(gitignored, regenerated from baserom on every `make setup`) into typed
C definitions in the corresponding `src/<TU>.c` (tracked). Each migrated
symbol stops being "raw bytes from the original ELF" and starts being
the developer's clean-room reconstruction — which is the bit that
actually makes the `.data` / `.rodata` percentages move (`tools/progress.py`
only credits .o bytes whose source is git-tracked).

---

## What "matching" data means here

The data pipeline lives in three tools (read `decomp/NOTES.md` →
"Migrating data sections from asm to src" for the full architecture):

1. `tools/build_data_tu_map.py` parses every text function's
   `%hi/%lo/%gp_rel` references, looks up the function's TU in
   `decomp/tu_map.json`, votes (symbol → owning TU), and writes
   `decomp/data_tu_map.json`. Symbols with no votes propagate by
   VMA proximity from the nearest voted neighbor.
2. `tools/migrate_data_per_tu.py` walks every `D_<VMA>` dlabel in
   `asm/data/cod/*.s`, extracts its raw bytes, and emits a definition
   per block into `src/<TU>_data.c` (e.g. `src/Basic_data.c`,
   `src/ios/cdvd_data.c`). Each definition uses
   `__attribute__((section(".X.0xVMA")))`; `SORT_BY_NAME` in the
   linker places it at the right offset regardless of source .o.
3. `tools/rewrite_data_named_sections.py` scans every `src/**/*.c`
   for those section attributes and strips the corresponding blocks
   from the asm-side blob so we don't get duplicate-definition link
   errors.

`make setup` runs all three. The committed pool-style files
(`src/cod/sdata_pool.c`, `src/cod/lit4_pool.c`) and the auto-generated
per-TU `*_data.c` files coexist — `_data.c` migrators skip symbols
already defined in any non-`_data.c` source.

**The matching loop**: pick one `_data.c`, type its symbols, save them
into the non-`_data.c` companion file (`src/Basic.c`, etc.), commit.
On the next `make setup`, the migrator re-detects the now-typed
definitions and drops them from the auto-generated `_data.c` (its
`_scan_existing_definitions()` skip-set picks them up).

## Do not break SHA-1

The only correctness signal is `make` round-tripping to
`fbf50c75cd5911273511c4f9af90503ff8423582`. `tools/quick_diff.sh` only
checks .text — it's blind to data-section divergence. Always run the
full `make && verify-target` cycle after each typed symbol.

If SHA-1 fails:

* `tools/first_diff.py` localizes which byte / function / section
  diverged.
* Common culprits: endianness on multi-byte fields (always
  little-endian on R5900), `char` signedness, struct padding (use
  `__attribute__((packed))` if uncertain), implicit string null
  termination (`char[N] = "foo"` doesn't pad to N — explicit nulls
  may be needed).

## Pick a TU to attack

Open `decomp/data_tu_map.json` for the symbol-to-TU mapping and
`docs/PROGRESS.md` for current data-section percentages. Good first
TUs:

* **Small `_data.c` files** — single-pass conversion is easy when
  there are <100 symbols.
* **TUs you've already started in .text** — `src/Basic.c` is a good
  one (already promoted, has the file-level `/* TU range */`
  preamble).
* **TUs that anchor multiple .text references** — improves the
  per-TU "real-decomp" coverage.

Steer clear of `_unassigned_data.c` until the TU map gets better
text-side coverage; symbols there got assigned by VMA proximity, not
votes, so the bucket is more likely to be misclassified.

## Recognize byte-array shapes

The migrator emits two basic shapes:

```c
// 8-aligned VMA, any block size: one unsigned char array
__attribute__((section(".rodata.0x00553730"))) unsigned char D_00553730[8] =
    { 0x30, 0x2E, 0x25, 0x64, 0x00, 0x00, 0x00, 0x00 };

// misaligned VMA: per-VMA single-element chunks
__attribute__((section(".rodata.0x0055CFFC"))) unsigned int D_0055CFFC = 0x12345678;
__attribute__((section(".sdata.0x006331B3"))) unsigned char D_006331B3 = 0x70;
```

Catalog of patterns to recognize when typing:

| Bytes look like… | Type it as… |
|---|---|
| Printable ASCII ending in `0x00` | `static const char D_X[] = "...";` |
| 4-byte word `0x3F800000` / `0x40000000` etc. | `float D_X = 1.0f;` / `2.0f` etc. (decode with `struct.unpack('<f', bytes.fromhex('00 00 80 3F'.replace(' ', '')))`) |
| 8-byte pair where high word ≈ `0x3F…3FF` | `double D_X = ...;` (only in `.data` — `-G 8` keeps doubles out of sdata/lit4) |
| 4-byte values resolving to `func_<vma>` in `build/ico.us.map` | `static void (*const D_X[N])() = { func_a, func_b, ... };` (function-pointer table) |
| Repeating 0x10 / 0x20 / 0x40-byte block | A struct array — introspect with `objdump -s -j .rodata baseelf.elf` and the .text indexing pattern |
| 4-byte values resolving to `D_<vma>` data symbols | `static void *D_X[] = { &D_a, &D_b, ... };` or typed pointer array |
| `jtbl_<VMA>` (auto-generated as `.word .L<text-vma>` originally) | Stays on the **asm side** — the migrator deliberately skips it because the bytes are .text VMAs that need linker resolution. Hand-type as `static void *jtbl_X[] = { &&L0, &&L1, ... };` only inside the function that owns it. |

Cheat sheets:

* `python -c "import struct; print(struct.unpack('<f', bytes.fromhex('XXXXXXXX'))[0])"` decodes a 4-byte hex word as float.
* `python -c "import struct; print(struct.unpack('<d', bytes.fromhex('XXXXXXXXXXXXXXXX'))[0])"` decodes 8-byte double.
* `objdump -s -j .rodata baserom/baseelf.elf | less` shows the raw bytes for any rodata VMA — useful for cross-checking your interpretation against ground truth.
* `grep '<VMA>' build/ico.us.map` resolves a 4-byte word that looks like a text VMA to a function name.

## The migrator's exact emission shape is load-bearing

`tools/rewrite_data_named_sections.py` strips a symbol from the asm
side **iff** it can match `__attribute__((section(".X.0xVMA"))) <type> D_<VMA>`
in some `src/**/*.c`. If your hand-typed definition uses a *slightly*
different shape — multi-line section attribute, different whitespace,
forward declaration before the section attribute, etc. — the regex
won't see it and you'll get duplicate-definition link errors. Keep
the section attribute and the `D_<VMA>` name on the **same line** at
the top of the definition. Examples that work:

```c
__attribute__((section(".rodata.0x00553730"))) static const char D_00553730[] = "0.%d";
__attribute__((section(".sdata.0x00631BC0"))) float D_00631BC0 = 1.0f;
```

Examples that DO NOT work (won't be stripped from asm, will collide
at link time):

```c
// section attr on its own line — regex needs it inline
__attribute__((section(".rodata.0x00553730")))
static const char D_00553730[] = "0.%d";

// symbol name renamed — regex looks for D_<VMA>
__attribute__((section(".rodata.0x00553730"))) static const char msg_e_d[] = "e+%d";
```

If you must rename a symbol for readability, **keep the `D_<VMA>` name**
and add an `#define readable_name D_<VMA>` macro or a `static const char
* const readable_name = D_<VMA>;` alias. Same applies to renaming jtbls
or function-pointer tables.

## Workflow

1. **Pick a TU.** Find its `_data.c` (`ls src/*_data.c src/*/*_data.c`).
2. **Identify the destination .c.** Drop the `_data` suffix:
   `src/Basic_data.c` → `src/Basic.c`. If the destination doesn't exist
   yet, create it with a preamble comment describing the TU's VMA
   range (see `src/Basic.c` for the format — it's the existing
   promoted reference).
3. **Type one symbol.** Open the `_data.c`, grab one definition,
   re-type it into the destination .c with the most natural C shape
   you can justify. Keep the section attribute and `D_<VMA>` name
   on the leading line.
4. **Rebuild.** `make && verify-target`. If SHA-1 fails, run
   `tools/first_diff.py`, fix, repeat.
5. **Commit.** One commit per TU's data-side migration, or one per
   logical group within a TU if the TU is huge. Commit message
   format mirrors the rest of the repo (read recent commits) — no
   AI co-author trailer.
6. **Verify the auto-generated sidecar shrinks.** On the next
   `make setup`, your typed symbols should disappear from
   `src/<TU>_data.c` because the migrator's
   `_scan_existing_definitions()` picks them up.

After several TUs, expect `tools/progress.py`'s `.data` / `.rodata` /
`.sdata` / `.lit4` percentages to climb from 0% toward 100% one TU
at a time. (They show 0% at session start because the only thing
currently "typed" data-side is the pool files and `src/Basic.c`'s
hand-promoted bits — most data lives in gitignored sidecars and
doesn't count.)

## Edge cases / when to back off

* **`func_*` references in `.word`** — the migrator already skips
  these (`_extract_bytes` returns `None` for non-literal operands)
  so they stay on the asm side until you type them as a function-
  pointer array. Look for `extern void func_X(...);` in the
  destination .c to confirm the function is declared.
* **Cross-TU symbols** — a symbol whose `data_tu_map` assignment is
  wrong because votes were ambiguous. Symptom: typing it in TU `A`
  works at the link level (SHA-1 OK), but you can tell from the
  text-side references that TU `B` actually owns it. Move the
  definition; the migrator will follow on next regenerate.
* **`_pad_<VMA>` continuation symbols** — chunked-emission artifacts
  from the migrator for misaligned VMAs. They're not real symbols
  from the asm side; they're synthetic. When you hand-type, fold
  the pad bytes into the parent block's array.
* **Symbols already in `src/cod/sdata_pool.c` / `src/cod/lit4_pool.c`** —
  these legacy pool files are still tracked. As you type, prefer
  moving definitions OUT of the pools and INTO their owning TU's
  `.c` (next to function definitions, parappa2-style). Eventually
  the pool files end up empty and can be deleted.

## Quick reference

* Asm side ground truth: `asm/data/cod/{531900.sdata,530900.lit4,453700.rodata,174700.data}.s`
* Raw bytes: `objdump -s -j .rodata baserom/baseelf.elf` etc.
* Linker map: `build/ico.us.map` (resolves any VMA to a symbol name)
* Symbol → TU map: `decomp/data_tu_map.json`
* TU placeholders (one per original `__FILE__` anchor): `decomp/source_tree/`
* Architecture deep-dive: `decomp/NOTES.md` → "Migrating data sections from asm to src"
* SHA-1 target: `fbf50c75cd5911273511c4f9af90503ff8423582` (recorded in `config/sha1sums.txt`)

When in doubt, **type one symbol, rebuild, verify SHA-1.** The build
is the truth.
