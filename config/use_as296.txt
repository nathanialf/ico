// TUs assembled with the LATER PERIOD assembler ee-as 2.96
// (GNU as 2.10-ee-001003-1, Oct 2000 — tools/cc/ee-gcc2.96/bin/as) instead of
// the default ee-as 2.9-991111.
//
// This is NOT the retired use_modern_as.txt. Modern gas (mips-linux-gnu-as) is
// gone for good (2026-08-05) and must stay gone. Both entries here are PERIOD
// assemblers shipped with the two ee-gcc toolchains; picking between them is a
// question about which toolchain built a given TU, and the whole-image SHA-1
// gate FALSIFIES a wrong answer — a TU assembled by the wrong one breaks its
// already-matched sibling functions immediately. That is what makes this a
// measurement rather than an escape hatch, and it is why a match landed under
// this list is a real match while one landed under modern gas was not.
//
// THE DIFFERENCE THAT MATTERS: 2.9-991111 performs NO delay-slot filling at all
// (probed 2026-08-05 with three hand-written bodies before a `j $31` — a dsll/
// dsra macro pair, the native dsll32/dsra32 form, and a plain non-macro daddu:
// all three came out `jr ra; nop`). 2.96 DOES fill in `.set reorder` mode. So a
// function whose ROM tail carries a real instruction in the `jr $31` slot, where
// gcc itself provably cannot put one, is evidence its TU went through 2.96.
//
// gcc cannot put one when the candidate's `length` attribute is not 1:
// mips.md's `(define_delay (eq_attr "type" "jump") [(and (eq_attr "dslot" "no")
// (eq_attr "length" "1")) ...])` admits only single-insn candidates, and every
// DI->SI narrowing pattern (truncdisi2 and the three anonymous truncate+shift
// combiner patterns) is hardcoded length 2 — including the arm that prints a
// single `dsra`. Only ashrdi3_internal4 is length 1, and reaching it needs an
// `x<<32>>32` pair that combine folds unconditionally into extendsidi2.
//
// WHY 2.9-991111 REMAINS THE DEFAULT: it is correct everywhere else, and 2.96
// OVER-fills relative to the ROM in two measured shapes — a `j <func>` tail call
// preceded by an unaligned store (0 of 783 ROM tail-calls carry one in the
// delay) and a `jr $31` preceded by an FP store/convert (0 ROM funcs have cvt in
// a jr delay). compile_c.sh neutralises both universally with `.set noreorder`
// wraps, which is why listing a TU here is safe, but do not read that as
// "2.96 everywhere would work" — it would not.
//
// HOW TO ADD ONE: only on ROM evidence that gcc cannot emit the tail, and only
// if the full `ninja` SHA-1 gate stays green afterwards. Never to make a diff go
// away. quick_diff.sh honours this file too, so the fast loop and the real build
// agree (without that, this TU reads a PHANTOM 2-insn scheduling diff forever).
//
// vendor_2575C0: func_00258450 (a 7-insn bit-stream "peek n bits" leaf) ends
//   `dsll32 v0 / jr ra / dsra32 v0` — the second half of gcc's two-line, length-2
//   truncdisi2 template sitting in the delay slot, which only an assembler can
//   put there. Landed as real C 2026-08-05; whole image stayed fbf50c75.
//   The only other `dsra32`-in-a-jr-slot site in the entire splat asm tree is
//   func_001011E8 in vendor_100C90 — also a src/cod/vendor_* TU, and itself
//   carrying three UNSPLIT dsll32/dsra32 pairs in its body, which is ROM-side
//   proof the pair is one compiler insn and the tail split is the assembler's.
//   Working hypothesis worth testing when that TU comes up: the third-party
//   `src/cod/vendor_*` code was built with the later toolchain while the game's
//   own TUs used 2.9-991111.
