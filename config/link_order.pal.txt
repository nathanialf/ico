# config/link_order.pal.txt: the objects of the PAL link, one per line, in link order.
#
# The order is the retail link's object order as MAIN.MAP gives it: every
# output section of config/link.pal.ld takes its inputs in this one order.
# The file is hand-maintained. It was derived once (2026-09-30) from the object
# order of config/ico.pal.d, the five VU microprograms and the data-only members
# placed where MAIN.MAP puts them. tools/gen_ninja_plain.py reads it and fails
# on any tracked .c/.s/.dsm under ico2/ or sce/ that is missing here, and on any
# listed file that does not exist.
#
# Line forms:
#   <path>             a source file (.c compiled by tools/compile_c.sh, .s
#                      assembled per archive, ico2/vusrc/*.dsm by dvp-as)
#   data:<member>      a data-only ico2000.a member: every row of
#                      config/data_members.pal.txt for it, extracted from the
#                      user's base ELF by tools/extract_data.py. Inside each
#                      run of them the order is MAIN.MAP's: its sections keep
#                      their ROM order and interleave by member name.
#
# Transitional forms, all gone at the cut-over (the generator counts them):
#   blob:cod/<name>    a splat blob, asm/data/cod/<name>.s, not carved yet
#   part:<path>        a later run of <path>'s sections, placed here
#   <sec>=<sel>,...    this line's input-section selectors for output section
#                      <sec> (data or rodata) instead of the whole section;
#                      "-" places none of them here
#   align.<sec>=16     the ROM starts this object's <sec> 16-aligned after fill
#                      that its own section alignment does not produce
# While any line carries a part: or a <sec> token, the generator lists .data
# and .rodata input by input (build/plain/<sec>.inputs.ld, INCLUDEd by the
# script); with none, those files are empty and the script's wildcards alone
# place the sections.
#
# Not listed: splat's cod/18ECB0 (the 80 zero bytes after .vutext; .reginfo is
# not allocated, the gap is fill), cod/44D320.data (zero bytes past the end of
# .data) and cod/539C54.lit4 (zero bytes past the end of .lit4).
# data:staffroll_dat is not listed yet: its three rows sit inside
# blob:cod/3E4610.data, blob:cod/51DF5C.rodata and blob:cod/53B518.sdata beside
# code-TU bytes that P1 has not carved.
